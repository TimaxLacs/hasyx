# Детальный план реализации голосового ассистента

Этот документ служит пошаговым руководством для реализации архитектуры, описанной в `voice-integration-plan.md`. Все изменения должны быть внесены в файлы `lib/voice.ts` и `lib/voice-device.ts`.

---

## ✅ Phase 1: Фундаментальный рефакторинг `voice.ts`

**Цель:** Заложить прочный фундамент для класса `Voice`, сделав его модульным, управляемым и расширяемым.

### ☐ **Задача 1.1: Определить интерфейсы и состояния**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Создаем `enum VoiceState` со всеми состояниями (`IDLE`, `INITIALIZING`, `LISTENING_FOR_KEYWORD`, `RECORDING_COMMAND`, `AWAITING_AI_RESPONSE`, `SPEAKING`, `DESTROYING`).
    2.  Определяем интерфейс `ITranscriber` с методами `initialize`, `start`, `stop`, `destroy`.
    3.  Определяем интерфейс `ITextToSpeech` с методами `initialize`, `speak`, `stop`, `destroy`.
*   **Зачем это нужно:** Это формализует контракт для всех состояний и движков, позволяя в будущем легко заменять реализации (Dependency Injection).

### ☐ **Задача 1.2: Реализовать State Machine и жизненный цикл**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  В классе `Voice` удаляем все старые флаги (`isProcessing`, `isListening` и т.д.).
    2.  Добавляем приватное свойство `private state: VoiceState = VoiceState.IDLE;`.
    3.  Реализуем публичные методы `async initialize()` и `async destroy()`.
        *   `initialize()`: должен проверять, что текущее состояние `IDLE`, а затем переводить его в `INITIALIZING` и `LISTENING_FOR_KEYWORD`.
        *   `destroy()`: должен переводить систему в `DESTROYING`, выполнять очистку и завершаться в состоянии `IDLE`.
*   **Зачем это нужно:** Для предсказуемого и надежного управления ресурсами и состоянием ассистента.

### ☐ **Задача 1.3: Создать классы-реализации по умолчанию**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Создаем класс `VoskTranscriber implements ITranscriber`. Переносим в него всю логику, связанную с `Vosk` и `arecord` из старого класса `Voice`.
    2.  Создаем класс `ZonosTTSEngine implements ITextToSpeech`. Переносим в него всю логику, связанную с запуском сервера `zonosjs` и генерацией речи.
*   **Зачем это нужно:** Чтобы отделить конкретные реализации от основной логики класса `Voice`, следуя принципу инверсии зависимостей.

### ☐ **Задача 1.4: Обновить конструктор `Voice`**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Модифицируем конструктор `Voice`, чтобы он принимал объект `options`.
    2.  В `options` добавляем необязательные поля: `transcriber: ITranscriber`, `tts: ITextToSpeech`, `enableTranscription: boolean`, `enableTTS: boolean`.
    3.  Внутри конструктора, если `transcriber` или `tts` не предоставлены, создаем экземпляры `VoskTranscriber` и `ZonosTTSEngine`.
    4.  Сохраняем опции для использования в методе `initialize`.
*   **Зачем это нужно:** Чтобы сделать класс `Voice` гибко конфигурируемым и позволить пользователям внедрять свои собственные реализации STT/TTS.

## ✅ Phase 2: Интеграция с AI

**Цель:** Подключить ассистент к центральной AI-архитектуре Hasyx.

### ☐ **Задача 2.1: Интегрировать `Dialog`**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Добавляем в `Voice` приватное свойство `private dialog?: Dialog;`.
    2.  В методе `initialize()`, создаем экземпляр `Dialog`, передавая ему `AIProvider`, инструменты (`ExecJSTool`, `TerminalTool`) и системный промпт.
    3.  В качестве `onChange` для `Dialog` передаем ссылку на новый метод `this.handleDialogEvent.bind(this)`.
*   **Зачем это нужно:** Чтобы делегировать всю логику управления диалогом, инструментами и общением с LLM стандартному компоненту Hasyx.

### ☐ **Задача 2.2: Реализовать `handleDialogEvent`**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Создаем приватный асинхронный метод `handleDialogEvent(event: DialogEvent)`.
    2.  Реализуем логику для каждого типа события (`ai_response`, `tool_call`, `done`, `error`), которая будет управлять переходами конечного автомата (`VoiceState`).
    3.  При событии `ai_response`, вызываем метод `this.tts.speak(...)`.
*   **Зачем это нужно:** Это "реактор" нашего ассистента, который преобразует события от AI в действия (смена состояний, озвучивание ответа).

### ☐ **Задача 2.3: Рефакторинг метода `ask`**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Полностью переписываем метод `ask(command: string)`.
    2.  Его единственной задачей становится вызов `this.dialog.ask({ role: 'user', content: command })`.
    3.  Метод также должен переводить `VoiceState` в `AWAITING_AI_RESPONSE`.
*   **Зачем это нужно:** Для упрощения API и следования принципу единой ответственности.

## ✅ Phase 3: Реализация аудиовывода

**Цель:** Заставить ассистента физически говорить.

### ☐ **Задача 3.1: Добавить воспроизведение в `AudioDeviceManager`**
*   **Файл:** `lib/voice-device.ts`
*   **Что делаем:**
    1.  Добавляем в класс `AudioDeviceManager` новый публичный метод `playAudio(buffer: Buffer)`.
    2.  Внутри этого метода используем системную утилиту (`aplay` для Linux, `afplay` для macOS) для воспроизведения аудио из буфера.
*   **Зачем это нужно:** Чтобы централизовать всю работу с аудио-устройствами в одном классе.

### ☐ **Задача 3.2: Связать TTS с воспроизведением**
*   **Файл:** `lib/voice.ts`
*   **Что делаем:**
    1.  Класс `ZonosTTSEngine` должен принимать в конструкторе экземпляр `AudioDeviceManager`.
    2.  В методе `speak(text: string)`, после получения аудио-буфера от `zonosjs`, вызываем `this.audioDeviceManager.playAudio(buffer)`.
    3.  `Voice` должен создавать и передавать экземпляр `AudioDeviceManager` в `ZonosTTSEngine`.
*   **Зачем это нужно:** Чтобы замкнуть цикл: сгенерировали речь -> воспроизвели ее.
